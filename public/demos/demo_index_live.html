Part 1 · Architecture

How the system is built

Every piece of the system has one job. Raw records become typed objects; typed objects accumulate into per-entity profiles; rules read profiles and emit alerts; a manager ranks the alerts; a reporter renders them. Each stage talks to the next through a small, stable interface, so any one piece can change without disturbing the rest.

Trade / Transaction → EntityProfile → DetectionRule → Alert → AlertManager → ReportGenerator

1.1 · The rule hierarchy

All six detectors descend from one abstract base. Two intermediate classes split the world into market-surveillance and payment-fraud rules, and each binds itself to the kind of entity it applies to. Adding a seventh rule means adding a subclass — nothing else in the system changes.

detection_rules.py
class DetectionRule(ABC):
    def __init__(self, rule_name, severity, time_window_seconds):
        if time_window_seconds <= 0:
            raise InvalidThresholdError(...)   # fail fast on bad config
        self.rule_name = rule_name
        self.severity  = severity

    @abstractmethod
    def detect(self, profile): ...        # every rule must implement this

class MarketRule(DetectionRule, ABC):
    profile_type = TraderProfile          # applies to traders

class FraudRule(DetectionRule, ABC):
    profile_type = CustomerProfile        # applies to customers
Why it matters: the abstract detect() is the contract. The main loop calls rule.detect(profile) without ever naming a concrete class — the right version runs based on the object's real type. That's polymorphism doing the routing.

1.2 · The Alert — an immutable record

An alert is evidence, and evidence shouldn't change after it's written. Alerts are a frozen dataclass: severity is normalized once at construction, every alert gets a unique ID, and any attempt to mutate one raises an error.

alert.py
@dataclass(frozen=True)
class Alert:
    rule_name: str
    entity_id: str
    severity:  str            # normalized to UPPER in __post_init__
    message:   str
    evidence:  tuple = ()
    timestamp: str = field(default_factory=now_iso)
    alert_id:  str = field(default_factory=next_id)   # ALT-00001, ALT-00002...
A real bug this fixed: in an earlier version, detectors emitted "High" while the manager expected "HIGH", so a medium alert once outranked two high ones in a live log. Normalizing inside the constructor made the mismatch impossible everywhere at once.

1.3 · Type-safe dispatch

Because each rule declares its profile_type, the orchestrator can only ever hand a trader profile to a market rule and a customer profile to a fraud rule. An invalid pairing isn't caught at runtime — it's structurally impossible.

main.py — dispatch loop
for profile in profiles.values():
    for rule in rules:
        if isinstance(profile, rule.profile_type):
            manager.add_alerts(rule.detect(profile))
Part 2 · The Rules

Six detectors, two domains

Three rules watch trading activity for market manipulation; three watch payment activity for fraud. Each reads only the events inside its own time window and raises an alert when a pattern crosses its threshold.

RULE 2.1 Wash trade detection

A wash trade is a buy and a sell of the same security, by the same trader, at nearly the same size and time — activity that looks like trading but moves no real ownership. The detector pairs buys against sells and flags any pair inside the window whose volumes overlap past a threshold.

WashTradeDetector.detect()
buys  = [t for t in trades if t.order_type == "BUY"]
sells = [t for t in trades if t.order_type == "SELL"]
for buy in buys:
    for sell in sells:
        overlap = min(buy.volume, sell.volume) / max(buy.volume, sell.volume)
        if buy.symbol == sell.symbol \
           and buy.time_diff(sell) <= self.time_window_seconds \
           and overlap >= self.volume_overlap_pct:
            alerts.append(self._make_alert(...))   # round-trip found
Complexity note: pairing buys against sells is O(n²) in the worst case, but only within a bounded time window — so in practice it's O(n·k) where k is the number of trades per window. Narrowing the window directly shrinks the comparison set.

RULE 2.2 Spoofing

A large order placed and then cancelled within seconds can be an attempt to mislead others about supply or demand. The detector links each cancellation back to its placement by order ID and measures the gap.

A bug this rule taught me: the first version put the return inside the cancel loop, so only the first cancellation was ever checked — a spoofer who cancelled several orders would have all but one slip through. A regression test now guards against it.

RULE 2.3 Front running

Buying just before a large client order in the same security can indicate trading on advance knowledge of that order. The detector pairs each large client buy against the trader's own buys and checks that the trader's order landed before the client's, inside the window.

FrontRunningDetector.detect()
trader_buys = [t for t in trades if t.order_type == "BUY"]
client_buys = [t for t in trades if t.order_type == "CLIENT_BUY"
               and t.volume >= self.large_client_volume]

for client in client_buys:
    for buy in trader_buys:
        if buy.symbol == client.symbol and \
           0 < (client.timestamp - buy.timestamp).total_seconds() <= self.time_window_seconds:
            profile.update_risk_score("manipulation", 25)
            alerts.append(self._make_alert(...))
Note the strict 0 <: the trader's buy must come strictly before the client order, not after. Direction of time is what separates front-running from an ordinary trade that happens to sit nearby in the tape.

RULE 2.4 Velocity burst

An account making far more transactions than usual in a short window can signal automated or unauthorized activity. This rule is the simplest — count the in-window transactions, compare to a threshold — and the most linear: O(n) over the transactions, with O(1) lookups per account.

VelocityChecker.detect()
txns = self._get_transactions(profile)
if len(txns) > self.max_transactions:
    profile.update_risk_score("fraud", 25)
    return [self._make_alert(
        entity_id=profile.entity_id,
        description=f"{len(txns)} transactions in 
                    {self.time_window_seconds//60} minutes",
        evidence=[t.to_dict() for t in txns],
    )]

RULE 2.5 Time-of-day anomaly

Activity far outside an account's normal hours can signal a compromised account. Each customer profile carries its own active-hours window, so the rule compares against that account's pattern rather than one global schedule — with a buffer hour so ordinary early or late activity isn't flagged.

TimeOfDayAnomalyDetector.detect()
start_hour, end_hour = profile.active_hours     # lives on CustomerProfile
for txn in txns:
    hour = txn.timestamp.hour
    outside = hour < (start_hour - self.hour_buffer) \
           or hour > (end_hour + self.hour_buffer)
    if outside:
        profile.update_risk_score("fraud", 15)
        alerts.append(self._make_alert(...))
Why active_hours sits on CustomerProfile: traders don't have one — this is the single attribute that justified splitting the profile class into trader and customer subclasses instead of one shared type.

RULE 2.6 Amount threshold & structuring

Two patterns in one rule. A single transaction over the large-amount threshold is flagged directly. Separately, several transactions clustered just below that threshold suggest deliberate splitting to stay under a reporting limit — so the rule also scans a band set at 90% of the threshold and flags the group when enough transactions fall inside it.

AmountThresholdRule.detect()
# 1 — single large transaction
for txn in txns:
    if txn.amount >= self.large_amount:
        profile.update_risk_score("fraud", 30)
        alerts.append(self._make_alert(...))

# 2 — structuring: a cluster just under the limit
near = [t for t in txns
        if self.structuring_floor <= t.amount < self.large_amount]
if len(near) >= self.structuring_count:
    profile.update_risk_score("fraud", 35)
    alerts.append(self._make_alert(...))     # one alert for the pattern
This is the rule that fires twice in the demo run — once on C31's single $11,200 wire, once on C14's pair of wires in the $8,550–$9,500 band. That's why seven alerts come from six detectors.

3.2 · Why the numbers are provable

Because the data is labeled, detection quality is measured, not asserted: seven patterns seeded, seven detected on rule + entity + evidence, zero alerts on any clean probe. That exactness is the deliberate trade-off of synthetic data — real order-book feeds carry no manipulation labels, so ground truth there would require expert review.

The same detectors, unchanged, also run against real NASDAQ order-book data (LOBSTER) and a published payment simulator (PaySim) — only the loader class changes, never the detection logic. That separation of data from analysis is the whole point of the design.
